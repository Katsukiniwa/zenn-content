# OAuth/OIDCについて知ってること

とりあえず今の自分のOAuth/OIDCに対するイメージを、確度別に羅列。

## たぶん合ってる

- OAuthはアクセストークンを発行するまでのやり取りしか決まってないし、アクセストークンのフォーマットについても決まっていない、あくまで認可のプロトコル(フレームワーク)
- OAuthを拡張して認証にも使えるようにしたのがOIDCで、アクセスしてるのが誰かを示すIDトークンとリソースアクセス(認可)に使うトークンであるアクセストークンそれぞれを発行する
- IDトークンのフォーマットはOIDCの仕様としてJWTであることが決まっている
- アクセストークンのフォーマットは特に決まってない

## 合ってるか不安

- OAuthでは最終的にアクセストークンを発行してリソースサーバにアクセスするが `アクセストークンを持ってる = 認証済み` と判断するのは危険
  - なんでダメなんだろう？
- OIDCでは認証証明として認可サーバがアクセストークンと一緒にIDトークンを払い出す。IDトークンはクライアント(Relying Party)が読み込んで良い。
- IDトークン(JWT)はJWKを使って改ざんされていないか検証できる
  - JWKは公開鍵をJSONで表現したもので、URLで公開される
    - Cognitoの場合 `https://cognito-idp.<Region>.amazonaws.com/<userPoolId>/.well-known/jwks.json` の形式で公開されることが決まっている
    - [CognitoでJWTをJWKを使って検証する方法に関する公式ドキュメント](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-tokens-verifying-a-jwt.html)

## 分からない

- OIDCとOAuthの違い
  - OIDCではなぜ認証までできるのか？

# OAuthについて

## 登場概念

- リソースオーナー
  - いわゆるユーザーだと思って良さそう
- クライアント
  - Webアプリなりモバイル・デスクトップアプリなりソーシャルログイン機能を実装したアプリ
- リソースサーバー
  - GoogleとかX(Twitter)が提供するAPIサーバをイメージすれば良さそう
- 認可サーバ
  - GoogleとかXが提供するサーバでアクセストークンを発行してくれる

## 付与方式(グラント種別)

クライアントがWebアプリなのかブラウザ内アプリなのかネイティブアプリ(モバイル・デスクトップアプリ)なのかで、推奨されるアクセストークンを発行するまでのフローが違うらしい。

付与方式は5つある。

1. Authorization Code Grant Type
2. Implicit Grant Type(非推奨)
3. Client Credentials Grant Type
4. Resource Owner Credentials Grant Type(Password Grant Type)
5. Assertion Grant Type

この中で大事なのは1と2らしいので他の3つの付与方式のフローは後回しにする。

1と2の違いは、認可サーバからクライアントの/callbackに戻ってきた時に認可コードが渡されるのか、直接アクセストークンが渡されるのかの違いだけっぽい。
1の場合は渡された認可コードをもとに認可サーバのトークンエンドポイントを叩いてアクセストークン(+ リフレッシュトークン)をもらう必要があるのに対して、2では直接アクセストークンをもらえるのでトークンエンドポイントを叩く必要がない。

# OAuth認証の何がいけないのか？

ここが一番分からなかったところ。

結論 **「アクセストークンが奪われたら成りすまされてしまうから」**

## Implicit Grant Typeの場合

偽アプリなどで被害者のアクセストークンを盗んだ上で、/callbackエンドポイントにリダイレクトされた際、クエリパラメータに認可サーバから付与された自分(攻撃者)のアクセストークンではなく被害者のアクセストークンに入れ替えることで、リソースサーバに被害者としてアクセスしてデータを引き出せる、という寸法らしい。

**疑問点**

- アクセストークンを盗めたなら、わざわざ/callbackエンドポイントにリダイレクトされた際に自身のアクセストークンと交換せずとも、直接盗んだアクセストークンを使ってリソースサーバにアクセスすればいいだけなのでは・・・？

## Authorization Code Grant Typeの場合

こちらで盗むべきは認可コード。

/callbackでクエリパラメータに認可コードが渡ってくるので、それを被害者のものとすり替えてトークンエンドポイントへアクセストークンを取得しにいく。
しかしトークンエンドポイントへのリクエストには

- client_id
- client_secret
- 認可コード

を含める必要があり、偽アプリなどの他アプリで被害者の認可コードを取得しても、認可サーバ側でclient_id, client_secretが異なるため弾かれる。

つまりAuthorization Code Grant Typeでは、アクセストークンの奪取による他人のなりすましは不可能。

ただしこれはclient_secretを安全に隠しておけるサーバサイドアプリ(Confidential Client)の話で、SPAやネイティブアプリのようにclient_secretを埋め込めないアプリ(Public Client)だとこの前提が崩れる。そこで出てくるのがPKCEらしいが、まだ理解できていないので後述の宿題行き。

## どう防ぐか？

つまりアクセストークンが他アプリで発行されたものかどうかをチェックできればいい。

認可サーバにトークン検証用のエンドポイント(ex. /introspect)を用意してアクセストークンとclient_idを受け付けるようにする。認可サーバでは受け取ったアクセストークンとclient_idのセットがアクセストークン発行時と同じclient_idかどうかを検証してtrue/falseを返すようにする。
ログインフローの最後にこのトークン検証用のエンドポイントを叩くことで、アクセストークンのなりすましを防ぐことができる。

→ とはいえこれはOAuthで認証を頑張るための緩和策であって、素直にOIDCを使えという話らしい。

# OIDCについて

## 登場概念

- エンドユーザ
- リライング・パーティ
- IDプロバイダー(IdP)
- UserInfoエンドポイント

OAuthとの対応表は↓な感じ

| OAuth 2.0 | OpenID Connect (OIDC) |
| --- | --- |
| Resource Owner（リソースオーナー） | End User（エンドユーザー） |
| Client（クライアント） | Relying Party / RP（リライング・パーティ） |
| Authorization Server（認可サーバー） | OpenID Provider / OP（IdP） |
| Resource Server（リソースサーバー） | UserInfo Endpoint（＋任意の Resource Server） |

名前が違うだけでだいたい同じ、という理解で良さそう。

## フロー

OIDCではOAuthでいうGrant TypeのことをFlowという。
Flowには

1. Authorization Code Flow
2. Implicit Flow
3. Hybrid Flow

の3つがある。

**補足**

Implicit Flowってアクセストークンなりすませるやつじゃん、じゃあOIDCも認証ダメじゃん、と思うかもしれないが、OIDCではアクセストークンと一緒にIdP(認可サーバ)からIDトークンが返却され、RP(Relying Party = クライアント)側でIDトークンを検証することでアクセストークンのなりすましを検知するため、OAuthにおけるImplicit Flowが抱えていた課題は解決されている。

# IDトークンについて

詳細は [IDトークンが分かれば OpenID Connect が分かる](https://qiita.com/TakahikoKawasaki/items/8f0e422c7edd2d220e06) を読むのが早いです。

気になるのはどうやってIDトークンを検証するのか？だと思います。

鍵は `at_hash` です。

以下は上記の記事からの引用です。

> ID トークンと同時にアクセストークンも発行される場合、at_hash というクレームが追加されます。at_hash の値は、アクセストークンのハッシュをとり、結果として得られたハッシュ値の左半分のビット群を base64url でエンコードしたものです。同様に、認可コードが同時に発行される場合は、c_hash というクレームが追加されます。
>
> 加えて、nonce クレームが必須となります。

つまりIdPから受け取ったアクセストークンを自分でハッシュ化して、左半分のビット群をbase64urlでエンコードした値をIDトークンのat_hashと突き合わせれば、アクセストークンが入れ替えられていないか確認できます。

これが「OIDCではなぜ認証までできるのか？」の答えっぽい。
アクセストークンは単体では誰のものか分からないが、IDトークンが「このアクセストークンは確かにこのユーザーに対して私(IdP)が発行したものです」と署名付きで保証してくれる、という構図。

一般的なIDaaS(ex. Auth0, Firebase Authentication, Cognito)ではそれぞれのSDKにIDトークン検証用のメソッドが実装されているため、自力で実装する機会は少ないかもしれません。
以下はFirebase AuthenticationにおけるIDトークンの検証コードです。

```js
// idToken comes from the client app
getAuth()
  .verifyIdToken(idToken)
  .then((decodedToken) => {
    const uid = decodedToken.uid;
    // ...
  })
  .catch((error) => {
    // Handle error
  });
```

[ID トークンを検証する](https://firebase.google.com/docs/auth/admin/verify-id-tokens?hl=ja)

# まだ分かっていないこと

- PKCE
  - Public Clientでは認可コードを横取りされる余地があり、その対策がPKCEらしい
  - `code_verifier` と `code_challenge` を使うところまでは読んだが、なぜそれで防げるのかを人に説明できない
- 今Implicit Flowを選ぶ理由はあるのか
  - 非推奨と言われつつOIDCの仕様には残っている
  - 「Authorization Code Flow + PKCE を使っておけばいい」という理解で本当に良いのか
- IDトークンの検証項目
  - この記事ではat_hashしか触れていないが、実際は iss / aud / exp / nonce / 署名 も見る必要があるはず
  - SDKに任せた時に何がチェックされていて何がされていないのかを把握できていない
- 冒頭の疑問点
  - 「アクセストークンを盗めたなら直接リソースサーバを叩けばいいのでは？」がまだ腑に落ちていない
  - 攻撃者の目的がリソースの取得なのか、正規アプリへのログインなのかで話が変わる気がしている

未熟ゆえ間違い等あるかと思いますが、コメントでご指摘頂ければ幸いです🙏
